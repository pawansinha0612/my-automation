Q2What is Playwright and why would you choose it over Selenium?▼
CommonConcept
Your score: 7/10
Must cover
OSS by Microsoft — supports JS, TS, Python, Java, C# (not just JS/TS)
Auto-waiting — checks 5 actionability conditions before every action
Built-in test runner, assertions, reporters, trace viewer — Selenium needs separate tools
Chromium, Firefox, WebKit — Safari coverage without a Mac
Parallel execution native — Selenium needs Grid which is complex
Selenium supports many languages — it was written in Java, not Java-only
Ideal answer
“Playwright is an open source framework by Microsoft supporting TypeScript, JavaScript, Python, Java, and C#. The biggest advantage over Selenium is auto-waiting — Playwright automatically checks that elements are ready before acting, eliminating most flakiness. Selenium has no auto-wait so you add waits manually. Playwright comes with everything built in — test runner, assertions, reporters, trace viewer — whereas Selenium needs separate tools. For browsers it supports Chromium, Firefox, and WebKit giving Safari coverage without a Mac. Parallel execution is native — Selenium needs Grid which is complex to set up.”
Common mistake: saying “Selenium is Java-based.” Correct: “Selenium was originally written in Java but supports many languages including Python, C#, and JavaScript.”
Q3What is the Page Object Model and why do we use it?▼
CommonSenior
Your score: 8/10
Must cover
Each page = one class with all locators and actions for that page
Separates HOW you interact with a page from WHAT you test
UI change = fix one file, not 50 test files
Reusability — one LoginPage used by many test files
BasePage class for shared methods — shows senior knowledge
Ideal answer
“POM is a design pattern where each page of the app has its own class holding all locators and actions — that’s the HOW. What you want to verify lives in the test file — that’s the WHAT. The biggest benefit is maintainability: if a button label changes, I fix it in one page class, not 50 test files. Page classes are also reusable — my LoginPage is used by login tests, checkout tests, and any test needing authentication. I also use a BasePage for shared methods like waitForPageLoad.”
// Page class — HOW to interact
class LoginPage {
  constructor(page) {
    this.submitBtn = page.getByRole('button', { name: 'Submit' });
  }
  async login(user, pass) { /* fill and click */ }
}
// Test file — WHAT to verify
test('login fails', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.login('user', 'wrong');
  await expect(loginPage.errorMessage).toBeVisible();
});
Q4What is the difference between locator() and getByRole()? When do you use each?▼
CodeCommon
Your score: 8/10
Must cover
getByRole — semantic HTML elements with ARIA roles (button, link, heading, checkbox)
locator() — div, span, p — elements with no meaningful role
getByRole is more stable — roles don’t change with CSS redesigns
locator(’.class’) is most fragile — class names change with styling
Priority: getByRole → getByLabel → getByText → getByTestId → locator(’#id’) → locator(’.class’)
Ideal answer
“Both find elements on the page. getByRole targets elements by their ARIA role — button, link, heading, checkbox. These are preferred because roles don’t change when a developer restyles the page. locator() is for elements without a meaningful role — divs, paragraphs, spans — using CSS selectors. The priority order is getByRole first, getByLabel for inputs, getByText for paragraphs, getByTestId if data-testid exists, locator(’#id’) for unique IDs, and locator(’.class’) as last resort.”
// Priority — top to bottom
page.getByRole('button', { name: 'Submit' })    // best
page.getByLabel('Email Address')                // inputs with label
page.getByPlaceholder('Enter email')             // no label
page.getByText('Congratulations')               // paragraphs
page.getByTestId('submit-btn')                  // data-testid
page.locator('#error')                           // unique ID
page.locator('.btn-primary')                    // fragile
Q5What is auto-waiting in Playwright and how does it prevent flaky tests?▼
CommonSenior
Your score: 6/10 — strengthen this
The 5 actionability checks — memorise these
Attached to DOM — element exists in the page
Visible — not hidden by display:none or zero opacity
Stable — not animating, position unchanged between frames
Receives pointer events — nothing overlapping it
Enabled — not disabled on input or button
Ideal answer
“Auto-waiting is Playwright’s built-in mechanism that checks five conditions before executing any action: attached to DOM, visible, stable, enabled, and receives pointer events. It retries every 16ms until all pass or the 30-second timeout hits. This replaces all the manual WebDriverWait boilerplate from Selenium. Web-first assertions like expect(locator).toBeVisible() also auto-retry, so you never get false failures because the DOM hadn’t updated yet.”
// Selenium — manual, verbose
new WebDriverWait(driver, Duration.ofSeconds(10))
  .until(ExpectedConditions.elementToBeClickable(By.id('btn')));
// Playwright — zero boilerplate
await page.click('#btn'); // checks all 5 automatically
// Web-first assertions also auto-retry
await expect(page.locator('.status')).toHaveText('Saved');
Q6How do you handle authentication in your Playwright test suite?▼
SeniorCode
Your score: 7/10
Must cover
global.setup.ts logs in once per role, saves session to auth.json
page.context().storageState({ path: ’auth.json’ }) — the actual API call
playwright.config.ts: storageState: ’auth.json’ — auto-loads for every test
Multiple roles = multiple files (admin-auth.json, student-auth.json)
Login tests: test.use({ storageState: { cookies:[], origins:[] } })
auth.json in .gitignore — never commit session tokens
Ideal answer
“I use storageState. In global.setup.ts which runs once before all tests, I log in with each user role and save the session using page.context().storageState({ path: ’auth.json’ }). In playwright.config.ts I set storageState: ’auth.json’ so every test starts already authenticated. For 50 tests this saves around 150 seconds. Login tests override with test.use({ storageState: { cookies:[], origins:[] } }) for a fresh session. Auth files go in .gitignore.”
// global.setup.ts — runs once
await loginPage.login('admin', 'password');
await page.context().storageState({ path: 'auth.json' });
// playwright.config.ts
use: { storageState: 'auth.json' }
// login tests — fresh unauthenticated session
test.use({ storageState: { cookies: [], origins: [] } });
Q7What is network mocking and when would you use it?▼
SeniorCode
Your score: 8.5/10
Must cover
page.route() — the Playwright method for interception
Backend not ready — test UI independently of the API
Test edge cases — 500 error, empty response, timeout
Tests become deterministic — same fake data every run
Block third party scripts — analytics, tracking = faster tests
Ideal answer
“Network mocking intercepts HTTP requests and returns controlled responses without hitting the real backend. In Playwright I use page.route(). Main use cases: when the backend isn’t ready and we want to start UI testing early, testing edge cases like 500 errors or empty responses, and making tests independent of backend stability. I also block third party calls like analytics which speeds up execution. The key benefit is tests become deterministic — same fake data every run.”
// Return fake data
await page.route('**/api/orders', route => route.fulfill({
  status: 200, body: JSON.stringify([{ id: 'ORD-001' }])
}));
// Simulate server error
await page.route('**/api/orders', route => route.fulfill({ status: 500 }));
// Block analytics
await page.route('**analytics**', route => route.abort());
Q8How do you integrate Playwright tests into a CI/CD pipeline?▼
CommonSenior
Your score: 8/10
Must cover
GitHub Actions — .github/workflows/playwright.yml
Steps: checkout → install Node → npm ci → install browsers → run tests
npx playwright install --with-deps — installs OS-level browser dependencies
Secrets for credentials — never hardcode in yaml
retries: process.env.CI ? 2 : 0 — handle flakiness in CI
Upload playwright-report as artifact — downloadable for debugging
Ideal answer
“Playwright generates a GitHub Actions workflow file at .github/workflows/playwright.yml. It triggers on every push or PR to main, runs on a fresh Ubuntu runner, and goes through: checkout code, npm ci for dependencies, npx playwright install --with-deps to download browsers, then run tests. Credentials are stored as GitHub Secrets. I configure retries so flaky tests retry automatically. The HTML report is uploaded as an artifact with screenshots, videos, and traces for failed tests.”
# Key workflow steps
- uses: actions/checkout@v4
- run: npm ci
- run: npx playwright install --with-deps
- run: npx playwright test
  env:
    LOGIN_USERNAME: ${{ secrets.LOGIN_USERNAME }}
- uses: actions/upload-artifact@v4
  if: ${{ !cancelled() }}
  with: { path: playwright-report/ }
Q9What is the difference between beforeEach and fixtures?▼
SeniorConcept
Your score: 5/10 — strengthen this
The key difference — say this clearly
beforeEach — scoped to one describe block in one file
Fixtures — reusable across ALL test files in the entire project
Fixtures are injected automatically via destructuring { loginPage }
Fixtures handle teardown automatically after use()
Use beforeEach for navigation in one block; fixtures for shared page objects
Ideal answer
“Both handle test setup but at different scopes. beforeEach runs before every test in a specific describe block — scoped to that one file. Fixtures are more powerful — defined once and injected into any test across any file in the project. For example my loginPage fixture is available to login tests, checkout tests, and profile tests without any setup code in those tests. Fixtures also handle teardown automatically — anything after use() runs after the test completes.”
// beforeEach — one file, one block
test.beforeEach(async ({ page }) => { await page.goto('/login'); });
// Fixture — entire project, any file
loginPage: async ({ page }, use) => {
  const lp = new LoginPage(page);
  await lp.goto();
  await use(lp);       // test runs here
  // teardown here
}
// any test file
test('login', async ({ loginPage }) => { ... });
Q10A test is passing locally but failing in CI. How do you debug it?▼
SeniorCommon
Your score: 6/10 — strengthen this
Lead with Trace Viewer — always
Download playwright-report artifact from GitHub Actions
npx playwright show-report → click failed test → Trace tab
Timing — CI machines are slower, elements take longer to appear
Headless vs headed — some elements behave differently headless
Missing env variables — secrets not configured in CI
Test data — exists locally but not in CI environment
Ideal answer
“First I check if it’s consistent or flaky by looking at CI run history and adding retries. Then I download the playwright-report artifact from GitHub Actions and open it with npx playwright show-report — the trace viewer lets me replay exactly what happened step by step with screenshots, network calls, and console errors. Common causes: timing issues because CI machines are slower, headless mode differences, missing environment variables, and test data that exists locally but not in CI.”
// Debug tools in order
npx playwright show-report           // trace viewer — start here
npx playwright test --headed         // see the browser
npx playwright test --debug          // step through line by line
npx playwright codegen URL           // find correct locators
await page.pause();                  // pause at specific point

Key Concepts
Core patterns with code snippets for quick revision.
Fixtures vs beforeEach — the critical difference▼
beforeEach = one describe block, one file. Fixtures = entire project, any file. Fixtures are injected automatically and handle teardown after use().
// fixtures.ts — define once, use everywhere
export const test = base.extend({
  loginPage: async ({ page }, use) => {
    const lp = new LoginPage(page);
    await lp.goto();
    await use(lp);
  }
});
// any test file
test('works', async ({ loginPage }) => {
  await loginPage.login('user', 'pass');
});
Strict mode violation — cause and fix▼
Playwright throws when a locator matches more than one element. Fix by making the locator more specific.
// Matches h2 AND b inside it → strict mode violation
page.getByText('Your password is invalid!')
// Target specific element by ID
page.locator('#error')
// Filter by parent container
page.locator('div').filter({ hasText: 'invalid' })
Value matchers vs locator matchers — when to await▼
Locator matchers query the live DOM and auto-retry — always await. Value matchers check plain JS values — no await needed.
// Locator matchers — await always
await expect(page.locator('#error')).toBeVisible();
// Value matchers — no await
expect(response.status()).toBe(200);
expect(body.title).toBe('My Post');
Chaining locators — scoping inside elements▼
Every locator method returns another locator scoped inside the previous result. This prevents strict mode violations on repeated elements.
page.getByTestId('order-row')              // all rows
  .filter({ hasText: 'Samsung Galaxy' })   // one row
  .locator('.status')                      // cell inside it
API testing with the request fixture▼
Playwright has built-in API testing via the request fixture — no browser needed. Combine with UI tests for the API + UI hybrid pattern.
test('GET returns 200', async ({ request }) => {
  const res = await request.get('https://api.example.com/posts/1');
  expect(res.status()).toBe(200);
  const body = await res.json();
  expect(body.id).toBe(1);
});
