Playwright • Chapter 01
What is Playwright?
Open source E2E testing framework by Microsoft. Controls real browsers. Built for testing from day one.

Released in 2020, Playwright lets you write code that controls a real browser — clicking, typing, navigating — automatically. Multi-browser, multi-language, with a full test runner built in.

Why Playwright?

Auto-waiting
Checks 5 conditions before every action. No manual sleeps.
All browsers
Chromium, Firefox, WebKit (Safari) from one API.
Built-in everything
Test runner, assertions, reporters, trace viewer in one install.
Multi-language
TypeScript, JavaScript, Python, Java, C#.
Parallel by default
Tests run across workers simultaneously, zero config.
API + UI testing
Test REST APIs and browser UI in the same test file.

Playwright • Chapter 04
Locators
How you find elements. The right locator makes tests resilient to UI changes.
// Priority order — always try from top
page.getByRole('button', { name: 'Submit' })   // 1. Role — best
page.getByLabel('Email Address')               // 2. Label — for inputs
page.getByPlaceholder('Enter email')            // 3. Placeholder
page.getByText('Congratulations')              // 4. Text — paragraphs
page.getByTestId('submit-btn')                 // 5. TestId — data-testid
page.locator('#error-msg')                     // 6. ID — solid fallback
page.locator('.btn-primary')                    // 7. Class — fragile

Chaining — scope inside parent

page.getByTestId('order-row')
  .filter({ hasText: 'Samsung Galaxy' })
  .locator('.status')
getByText('Error') matches all elements containing that text including nested ones. Use locator('#error') or getByRole('alert') to be specific.
Playwright • Chapter 05
Actions & Assertions
Actions control the browser. Assertions verify outcomes. Always await both.

Actions

await page.goto('/login');
await page.getByLabel('Email').fill('user@example.com');
await page.getByLabel('Password').fill('secret');
await page.getByRole('button', { name: 'Login' }).click();
await page.getByRole('checkbox').check();
await page.getByRole('combobox').selectOption('option1');
await page.keyboard.press('Enter');

Web-first assertions (always await)

await expect(locator).toBeVisible();
await expect(locator).toHaveText('exact');
await expect(locator).toContainText('partial');
await expect(locator).toBeEnabled();
await expect(locator).toHaveValue('val');
await expect(locator).toHaveCount(3);
await expect(page).toHaveURL('/dashboard');

Value assertions (no await)

expect(response.status()).toBe(200);
expect(items).toHaveLength(3);
expect(body.title).toBe('Post');
If inside expect() is a Playwright locator pointing at the browser: always await. If it is a plain JS value: no await needed.
Playwright • Chapter 06
Auto-Waiting
Playwright checks 5 conditions before executing any action automatically. This eliminates most flaky tests.
1. Attached to DOM
Element exists, not detached.
2. Visible
Not hidden by display:none or zero opacity.
3. Stable
Not animating, position unchanged between frames.
4. Receives events
Nothing overlapping it like a loading spinner.
5. Enabled
Not disabled on input or button.

Playwright polls every 16ms until all conditions pass or the 30-second timeout expires.

// Selenium — 3 lines, manual
new WebDriverWait(driver, Duration.ofSeconds(10))
  .until(ExpectedConditions.elementToBeClickable(By.id('btn')));
driver.findElement(By.id('btn')).click();

// Playwright — zero boilerplate, 5 checks automatic
await page.click('#btn');

// Web-first assertions also auto-retry
await expect(page.locator('.status')).toHaveText('Saved');
Never commit page.waitForTimeout() to tests. It is a sleep. Always use web-first assertions instead.
Playwright • Chapter 07
Page Object Model
The most important pattern in automation engineering. Separates HOW you interact from WHAT you test.

LoginPage.ts

import { Page, Locator } from '@playwright/test';

export class LoginPage {
  readonly page: Page;
  readonly usernameInput: Locator;
  readonly passwordInput: Locator;
  readonly submitButton: Locator;
  readonly errorMessage: Locator;

  constructor(page: Page) {
    this.page          = page;
    this.usernameInput = page.getByLabel('Username');
    this.passwordInput = page.getByLabel('Password');
    this.submitButton  = page.getByRole('button', { name: 'Submit' });
    this.errorMessage  = page.locator('#error');
  }

  async goto() { await this.page.goto('/practice-test-login/'); }
  async login(user: string, pass: string) {
    await this.usernameInput.fill(user);
    await this.passwordInput.fill(pass);
    await this.submitButton.click();
  }
}

Clean test using POM

test('wrong password shows error', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.login('student', 'wrongpass');
  await expect(loginPage.errorMessage).toBeVisible();
});
If it touches the DOM (locators, clicks, fills) it goes in the page class. If it checks an outcome (expect) it goes in the test file.

fixtures.ts

import { test as base } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

type F = { loginPage: LoginPage };

export const test = base.extend<F>({
  loginPage: async ({ page }, use) => {
    const lp = new LoginPage(page);
    await lp.goto();     // setup before test
    await use(lp);        // test runs here
                          // teardown after use()
  },
});
export { expect } from '@playwright/test';

Playwright • Chapter 09
Authentication
Log in once, reuse the session. 50 tests x 3 seconds = 150 seconds saved.

global.setup.ts

import { chromium } from '@playwright/test';

async function globalSetup() {
  const browser = await chromium.launch();
  const page    = await browser.newPage();
  await page.goto('https://example.com/login');
  await page.getByLabel('Username').fill('student');
  await page.getByLabel('Password').fill('Password123');
  await page.getByRole('button', { name: 'Submit' }).click();
  await page.context().storageState({ path: 'auth.json' });
  await browser.close();
}
export default globalSetup;

playwright.config.ts

globalSetup: './tests/global.setup.ts',
use: { storageState: 'auth.json' },  // auto-loads every test

Override for login tests

test.describe('login flow', () => {
  test.use({ storageState: { cookies: [], origins: [] } });
});
Add auth.json to .gitignore. Contains session tokens — never commit to git.
Playwright • Chapter 10
Network Mocking
Intercept HTTP requests and return controlled responses without hitting the real backend.
// Fulfill — return fake response
await page.route('**/api/orders', route => route.fulfill({
  status: 200, contentType: 'application/json',
  body: JSON.stringify([{ id: 'ORD-001', status: 'Delivered' }])
}));

// Abort — simulate network failure
await page.route('**/api/orders', route => route.abort());

// Continue — let through, use for logging
await page.route('**/*', route => route.continue());

// Block analytics to speed tests up
await page.route('**analytics**', route => route.abort());
Playwright • Chapter 11
API Testing
Test REST APIs with the request fixture. Combine with UI for powerful hybrid tests.
test('GET returns 200', async ({ request }) => {
  const res  = await request.get('https://jsonplaceholder.typicode.com/posts/1');
  expect(res.status()).toBe(200);
  const body = await res.json();
  expect(body.id).toBe(1);
});

test('API + UI hybrid', async ({ request, page }) => {
  // Create via API (fast)
  const res = await request.post('/api/products', { data: { name: 'Widget' } });
  expect(res.status()).toBe(201);
  // Verify in UI
  await page.goto('/products');
  await expect(page.getByText('Widget')).toBeVisible();
});
Use API to create test data. Use UI only to verify what the user sees. Never create test data through the UI — it is slow and fragile.

Run tests automatically on every push. Playwright generates the workflow file for you.

  push:         { branches: [ main ] }

    timeout-minutes: 60

      - uses: actions/checkout@v4

6/10 — strengthen
Ideal answer

5/10 — strengthen
Ideal answer
"beforeEach runs before every test in a specific describe block — scoped to that one file. Fixtures are defined once and injected into any test across any file in the project. Cypress • Chapter 01
What is Cypress?
Frontend-focused E2E framework. Runs inside the browser. Great DX for React/Vue/Angular teams.

Cypress runs directly inside the browser unlike Playwright which uses external protocols. This gives unique capabilities but also important limitations.

Key strengths

Easy to learn
Readable syntax, excellent docs, popular with frontend devs.
Auto-waiting
Automatically retries commands and assertions until they pass.
Time-travel debugging
DOM snapshots for every command in the Cypress UI.
cy.intercept()
Network interception built in. Stub API responses easily.

Key limitations

No Safari
Chrome, Firefox, Edge only. No WebKit.
JS/TS only
Cannot use Python, Java, or C#.
No multi-tab
Cannot test across multiple browser tabs.
Parallel = paid
Requires Cypress Cloud paid plan.
Choose Cypress when: React/Vue/Angular app, no Safari needed, value DX, frontend-focused team.

Cypress • Chapter 05
Network & cy.intercept()
Excellent built-in network interception. Stub responses, simulate errors, wait for requests.
// Stub with fixture file
cy.intercept('GET', '/api/orders', { fixture: 'orders.json' });

// Stub with inline response
cy.intercept('GET', '/api/orders', {
  statusCode: 200,
  body: [{ id: 'ORD-001' }]
});

// Wait for a specific request
cy.intercept('POST', '/api/login').as('loginReq');
cy.get('button[type=submit]').click();
cy.wait('@loginReq');
cy.url().should('include', '/dashboard');

// Simulate error
cy.intercept('GET', '/api/orders', { statusCode: 500 });
Cypress • Chapter 06
Authentication
cy.session() caches login state and reuses it. Similar to Playwright's storageState.
// cypress/support/commands.ts
Cypress.Commands.add('login', (username, password) => {
  cy.session([username, password], () => {
    cy.visit('/login');
    cy.get('#username').type(username);
    cy.get('#password').type(password);
    cy.get('button[type=submit]').click();
    cy.url().should('include', '/dashboard');
  });
});

// In tests — session is restored from cache
beforeEach(() => {
  cy.login('student', 'Password123');
});

Cypress • Chapter 08
Cypress Interview Q&A
Most common Cypress interview questions.
Q1What is Cypress and how does it differ from Playwright?▼
Ideal answer
"Cypress runs directly inside the browser unlike Playwright which uses external protocols. This gives great developer experience and time-travel debugging but means no Safari support, no multi-tab testing, and parallel execution needs a paid dashboard. I choose Cypress for frontend-heavy React/Angular teams where DX matters most and Safari is not required. For anything requiring cross-browser, multi-language, or full API testing I would use Playwright."
Q2What is cy.intercept() and when would you use it?▼
Ideal answer
"cy.intercept() intercepts HTTP requests and lets you stub responses, simulate errors, or wait for requests to complete. I use it when the backend is not ready so I can test UI with mocked data, when testing error states like 500 responses, and when I need to assert that a specific API was called. You alias it with .as() and use cy.wait('@alias') to pause until that request completes."
Q3What are the key limitations of Cypress?▼
Ideal answer
"Four key limitations: no Safari or WebKit support. No multi-tab or multi-domain testing. Parallel execution requires the paid Cypress Cloud dashboard. JavaScript and TypeScript only — no Python, Java, or C#. These are why enterprise teams often choose Playwright for new projects, though Cypress remains popular for frontend-focused teams."

Appium • Chapter 01
What is Appium?
The Selenium of mobile. Open source framework for automating native iOS and Android apps.

Appium acts as a server that translates WebDriver commands into native mobile actions through XCUITest (iOS) and UIAutomator2 (Android). It is the industry standard for native mobile app testing.

Playwright vs Appium

FeaturePlaywrightAppium
Mobile webYes (emulation)Yes (real browser)
Native iOS appNoYes
Native Android appNoYes
Setup complexitySimpleComplex (Xcode, Android Studio)
Test speedFastSlower
Playwright for mobile web (websites on a phone). Appium for native mobile apps (.ipa and .apk files).

Appium • Chapter 03
Mobile Locators
Mobile locators are different from web. Use accessibility IDs, XPath, class names specific to native UI.
// Accessibility ID (recommended — works on both iOS and Android)
await driver.$('~LoginButton');

// Android: resource ID
await driver.$('android=new UiSelector().resourceId("com.app:id/username")');

// iOS: predicate string
await driver.$('-ios predicate string:label == "Login"');

// XPath (last resort — slow and brittle)
await driver.$('//android.widget.EditText[@text="Username"]');
Accessibility ID is the preferred locator. It works on both platforms and is stable. Ask developers to add accessibility labels to all interactive elements.
Appium • Chapter 04
Gestures & Actions
Mobile requires gestures that do not exist in web testing — tap, swipe, scroll, long press.
// Tap
await driver.$('~LoginButton').click();

// Type text
await driver.$('~UsernameField').setValue('student');

// Swipe up
await driver.execute('mobile: swipe', { direction: 'up' });

// Long press
const el = await driver.$('~MenuButton');
await driver.execute('mobile: longClickGesture', {
  elementId: el.elementId, duration: 2000
});

// Hide keyboard
await driver.hideKeyboard();

Appium • Chapter 07
Appium Interview Q&A
Most common Appium interview questions for mobile automation roles.
Q1What is Appium and how does it differ from Playwright for mobile?▼
Ideal answer
"Appium is an open source framework for automating native iOS and Android apps using the WebDriver protocol. It acts as a server translating commands into native actions through XCUITest for iOS and UIAutomator2 for Android. Playwright can only emulate mobile devices in a browser — it cannot test a real native app binary. Appium is the choice when you need to test .ipa or .apk files with real native UI elements and device gestures."
Q2What are Desired Capabilities in Appium?▼
Ideal answer
"Desired Capabilities are key-value pairs that tell Appium what device, platform, and app to use for the test session. The most important are platformName (iOS or Android), deviceName, platformVersion, app (path to the binary), and automationName (XCUITest for iOS, UiAutomator2 for Android). They are passed when creating the driver session."
Q3What locator strategy do you prefer for mobile and why?▼
Ideal answer
"I prefer Accessibility ID (~) because it works on both iOS and Android, making tests platform-agnostic and stable. It maps to the accessibility label on iOS and content-description on Android. XPath is a last resort because it is slow and breaks easily when UI structure changes. I work with developers to ensure all interactive elements have accessibility IDs."

Selenium • Chapter 04
Waits & Synchronisation
Selenium has no auto-waiting. You must add waits manually. This is the biggest source of flaky tests.
// 1. Implicit wait — global default
driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));

// 2. Explicit wait — recommended
const wait = new WebDriverWait(driver, Duration.ofSeconds(10));
wait.until(ExpectedConditions.elementToBeClickable(By.id('submit'))).click();

// Common ExpectedConditions
ExpectedConditions.elementToBeClickable(locator)
ExpectedConditions.visibilityOfElementLocated(locator)
ExpectedConditions.invisibilityOfElementLocated(locator)
ExpectedConditions.textToBePresentInElement(el, 'text')
ExpectedConditions.urlContains('/dashboard')
Never use Thread.sleep() in Selenium tests. Always use explicit waits. Playwright eliminates all of this with built-in auto-waiting.

Selenium Grid
Distributes test execution across multiple machines and browsers. What Playwright does natively for free.
# Start Grid (standalone mode)
java -jar selenium-server-4.x.jar standalone

# Or hub + node separately
java -jar selenium-server-4.x.jar hub
java -jar selenium-server-4.x.jar node --hub http://localhost:4444

// Point tests at Grid
const driver = await new Builder()
  .usingServer('http://localhost:4444')
  .forBrowser('chrome')
  .build();
Playwright runs parallel tests natively with zero configuration. Selenium needs Grid for the same capability — one of Playwright's biggest advantages.
Selenium • Chapter 06
Page Object Model in Selenium
POM is used in Selenium exactly as in Playwright. The pattern is identical, only the syntax differs.
// Java POM
public class LoginPage {
  private WebDriver driver;
  private By usernameField = By.id("username");
  private By passwordField = By.id("password");
  private By submitButton  = By.css("button[type=submit]");

  public LoginPage(WebDriver driver) { this.driver = driver; }

  public void login(String username, String password) {
    driver.findElement(usernameField).sendKeys(username);
    driver.findElement(passwordField).sendKeys(password);
    driver.findElement(submitButton).click();
  }
}
The POM pattern is identical between tools. Locators in the page class, assertions in the test. Only the API syntax differs.
Selenium • Chapter 07
Selenium Interview Q&A
Most common Selenium questions. Important even if you primarily use Playwright.
Q1What are the three types of waits in Selenium?▼
Ideal answer
"Implicit wait sets a global timeout for all findElement calls. Explicit wait uses WebDriverWait with ExpectedConditions to wait for a specific condition on a specific element — this is recommended. Fluent wait is like explicit wait but lets you configure the polling interval and which exceptions to ignore. Thread.sleep should never be used. Playwright eliminates all of this with built-in auto-waiting."
Q2What is Selenium Grid and when would you use it?▼
Ideal answer
"Selenium Grid distributes test execution across multiple machines and browsers in parallel. A hub coordinates and nodes register with specific browser and OS combinations. I would use it in a Selenium project needing cross-browser testing at scale. In Playwright this is not needed because parallel execution is native and built in."
Q3Why would you still choose Selenium over Playwright in 2025?▼
Ideal answer
"Three scenarios: needing Internet Explorer support for legacy enterprise systems, a Java-based team with an existing Selenium framework that would be costly to migrate, or a large enterprise where Selenium is the mandated standard. For any new project I would choose Playwright."
Q4What is StaleElementReferenceException and how do you fix it?▼
Ideal answer
"It happens when you hold a reference to a DOM element that has been removed and re-rendered since you found it. The fix is to re-find the element each time instead of caching it. Playwright avoids this completely because its locators are lazy — they re-query the DOM every time an action is performed."
